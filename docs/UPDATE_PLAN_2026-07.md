## 2) العيوب المؤكدة في دقة الأرقام

هذه ليست ملاحظات أسلوبية. كل واحد منها يُنتج **رقماً خاطئاً يراه المستخدم**.

### 🔴 ع-1 — حارس الخسارة اليومية يفقد صفقات المساء

**الخطورة: حرجة.** هذا العيب يمكن أن يُخسِر المستخدم حسابه الممول.

في `lib/engines/risk.js` يوجد تناقض داخلي بين سطرين:

```js
const today = options.today || tradingDayKey(options.now, timezone);  // سطر 52 — يحترم التوقيت
...
dayKey(trade.date || trade.closeTime)                                  // سطر 56 — لا يحترمه
// حيث dayKey = String(value).slice(0, 10)   ← قصّ نصّي أعمى على توقيت UTC
```

الطرف الأول يحسب اليوم بتوقيت نيويورك، والطرف الثاني يقصّ نص UTC. عند مقارنتهما،
كل صفقة أُغلقت بعد الساعة 8 مساءً بتوقيت نيويورك تحمل تاريخ **اليوم التالي** بـ UTC،
فتسقط من حساب خسارة اليوم.

**المفارقة:** ملف `lib/trading-day.js` يحذّر من هذا الخطأ بالحرف في تعليقه:
> «Using `toISOString().slice(0, 10)` rolls the day over at 00:00 UTC … That would
> wrongly reset the daily loss budget mid-session.»

التحذير مكتوب، والدالة الصحيحة موجودة، لكن `risk.js` لا يستدعيها للصفقات.

**إعادة الإنتاج:**
```bash
node -e "
const {buildRiskSnapshot}=require('./lib/engines/risk');
const data={
  accounts:[{id:'a',capital:100000,currentBalance:99000,dailyLoss:2,maxDrawdown:6}],
  trades:[{accountId:'a',date:'2026-07-27T01:00:00.000Z',netProfit:-1500}],
  openPositions:[],settings:{timezone:'America/New_York'}};
const s=buildRiskSnapshot(data,'a',{now:'2026-07-27T02:00:00.000Z'});
console.log('اليوم:',s.today,'| خسارة اليوم:',s.balances.todayClosedPnl,'| الحالة:',s.state);
"
```

**المخرج الفعلي:** `اليوم: 2026-07-26 | خسارة اليوم: 0 | الحالة: SAFE`
**المتوقع:** `خسارة اليوم: -1500` مع تنبيه اقتراب من الحد.

**السيناريو الواقعي:** متداول خسر 1,500$ في جلسة نيويورك المسائية، وحدّه اليومي
2,000$. التطبيق يقول له «متبقٍ لديك 2,000$» فيدخل صفقة أخرى — ويخرق الحد.
**التطبيق أعطاه الضوء الأخضر لخرق حسابه.**

### 🔴 ع-2 — تصنيف الجلسات معطّل عملياً

في `lib/engines/analytics.js` سطر 24:

```js
const match = String(value || '').match(/\s(\d{1,2}):/);   // يشترط مسافة قبل الساعة
```

هذا التعبير النمطي يطابق `"2026.07.27 13:00"` لكنه **لا يطابق** `"2026-07-27T13:00:00Z"`
لأن الفاصل حرف `T` لا مسافة. كما لا يطابق التاريخ المجرد `"2026-07-20"` الذي تكتبه
الواجهة للصفقات اليدوية (`renderer/app/11-actions.js` سطر 124).

في الحالتين تُرجع `-1` فتُصنَّف الصفقة `'After'`.

**إعادة الإنتاج:**
```bash
node -e "
const {buildAccountAnalyticsSnapshot}=require('./lib/engines/analytics');
const mk=(d,p)=>({accountId:'a',date:d,netProfit:p,resultR:p>0?1:-1});
const data={accounts:[{id:'a',capital:1e5,currentBalance:1e5}],
 trades:[mk('2026-07-20',500),mk('2026-07-21',-300),mk('2026-07-22',800)],
 openPositions:[],signals:[],backtestSignals:[],settings:{}};
console.log(JSON.stringify(buildAccountAnalyticsSnapshot(data,'a',{})
  .breakdowns.bySession.map(x=>({label:x.label,count:x.count}))));
"
```

**المخرج الفعلي:** `[{"label":"After","count":3}]` — الصفقات الثلاث كلها في سلة واحدة.

**الأثر:** «تحليل الجلسات» و«خريطة الحرارة» عنصران بارزان في الواجهة، وهما حالياً
**يعرضان عموداً واحداً لا معنى له** لكل مستخدم يسجّل صفقاته يدوياً. والأسوأ من
الفراغ أن الرقم يبدو صحيحاً وهو ليس كذلك.

**عيب ثانٍ في نفس الدالة:** حتى عند نجاح المطابقة، الساعة تُقرأ كما هي في النص بلا
أي تحويل زمني. صفقة من تقرير MT5 بتوقيت الخادم (GMT+3 غالباً) تُصنَّف بحدود
لندن/نيويورك المكتوبة في الكود دون تحويل — تصنيف خاطئ حتى في المسار الناجح.

### 🟠 ع-3 — محرك التحليلات لا يعرف المنطقة الزمنية إطلاقاً

`grep -c timezone lib/engines/analytics.js` → **صفر**.

بينما `risk.js` و`calendar.js` و`daily-review.js` كلها تستورد `trading-day`،
محرك التحليلات — وهو أكثر المحركات ظهوراً للمستخدم — يعمل على UTC خالص في:

- `byDay` و `byMonth` (سطر 55)
- الفلاتر `today` / `week` / `month` (سطر 122–124)
- خريطة الحرارة عبر `getUTCDay()` (سطر 274)

**النتيجة الملموسة:** الصفقة نفسها تظهر يوم 26 يوليو في صفحة التقويم، ويوم 27 يوليو
في صفحة التحليلات. صفحتان في تطبيق واحد تتناقضان أمام المستخدم.

```bash
node -e "
const {buildAccountAnalyticsSnapshot}=require('./lib/engines/analytics');
const data={accounts:[{id:'a',capital:1e5,currentBalance:1e5}],
 trades:[{accountId:'a',date:'2026-07-27T01:00:00.000Z',netProfit:500,resultR:1}],
 openPositions:[],signals:[],backtestSignals:[],settings:{timezone:'America/New_York'}};
console.log('التحليلات تضع الصفقة في:',
  buildAccountAnalyticsSnapshot(data,'a',{}).breakdowns.byDay[0].label);
console.log('التقويم يضعها في           : 2026-07-26');
"
```

## 3) الديون التقنية

### د-1 — الترحيل لا يُكمل الحقول الناقصة

`lib/store.js` يدمج المستوى الأعلى فقط. الحسابات القديمة تعبر كما هي:

```bash
node -e "
const {createStore}=require('./lib/store');
const fs=require('fs'),os=require('os'),path=require('path');
const dir=fs.mkdtempSync(path.join(os.tmpdir(),'z-'));
fs.writeFileSync(path.join(dir,'journal-data.json'),
  JSON.stringify({version:1,accounts:[{id:'fundingpips',firm:'FundingPips'}]}));
const st=createStore({getPath:()=>dir}).read();
console.log('الحساب بعد الترحيل:',JSON.stringify(st.accounts[0]));
console.log('الإصدار المسجل   :',st.version);
"
```

**المخرج:** `{"id":"fundingpips","firm":"FundingPips"}` مع `version: 4`.

الحساب يفتقد `capital` و`dailyLoss` و`maxDrawdown`، ومع ذلك خُتم بالإصدار 4.
المحركات تحوّل `undefined` إلى صفر، فتتعطل كل حدود المخاطرة **بصمت** — بلا رسالة
خطأ تكشف السبب. والختم بالإصدار 4 يجعل أي إصلاح لاحق غير قادر على تمييز البيانات
المعطوبة عن السليمة.

هذا هو البند **3.2** في `docs/DEVELOPMENT_PLAN.md` وما زال `⬜`.

### د-2 — تسع قنوات IPC مكشوفة بلا مستدعٍ

كل واحدة منها سطح هجوم مفتوح من الواجهة إلى العملية الرئيسية بلا فائدة مقابلة:

```
archiveAccount · archiveBacktest · archivePlaybook · completeOnboarding
getLocale · saveFundingUrl · setLocale · signalResult · stopBacktest
```

```bash
grep -oP '^\s+\K\w+(?=:)' preload.js | while read n; do
  [ "$(grep -rho "\.$n(" renderer/app/*.js | wc -l)" -eq 0 ] && echo "يتيمة: $n"
done
```

البند **3.4** في `DEVELOPMENT_PLAN.md`، ما زال `⬜`.

### د-3 — النافذة الرئيسية بلا `sandbox`

في `main.js`، نافذة الكشط المؤقتة (سطر 249) تُفعّل `sandbox: true`، بينما النافذة
الرئيسية (سطر 402) **لا تفعله**. الأضعف حمايةً هي التي تعمل طوال الوقت.
`preload.js` لا يستورد سوى `electron`، فالتفعيل لن يكسر شيئاً.

### د-4 — عدّاء اختبارات هشّ

`npm test` سلسلة من 28 أمراً موصولة بـ `&&`. أول فشل يوقف الباقي، فلا تعرف إن كنت
أمام عطل واحد أو عشرة — تُصلح وتُعيد وتنتظر، دورة بطيئة. ولا يوجد lint ولا
تنسيق ولا حقل `engines`.

### د-5 — تعذّر الوصول (a11y)

`renderer/index.html` فيه **1,119 سطراً و62 زراً وسمة `aria-` واحدة**. لا `role`،
لا `aria-label`، لا حصر تركيز داخل النوافذ المنبثقة. تطبيق عربي RTL موجّه لسوق
مهمل أصلاً — الوصول هنا ميزة تنافسية لا التزام شكلي.

## 4) الأمن والتبعيات

```
electron 37.10.3  →  43.2.0   (ستة إصدارات رئيسية للخلف)
17 ثغرة عالية الخطورة
```

من بينها: use-after-free متعددة، وحقن مفاتيح الريجستري على ويندوز، وحقن ترويسات
HTTP، وحقن مفاتيح سطر أوامر المُصيِّر. المنتج **يشحن مثبِّت ويندوز**، أي أن هذه
الثغرات تصل إلى جهاز المستخدم فعلياً.

`main.js` يستورد سبعة رموز فقط من `electron` (`app, BrowserWindow, ipcMain, dialog,
safeStorage, Notification, shell`)، وكلها مستقرة عبر الإصدارات — فالترقية منخفضة
المخاطر على الأرجح، لكن **التحقق النهائي يجب أن يتم ببناء ويندوز حقيقي**، لأن
Electron لا يعمل في هذه البيئة (`libnspr4.so` مفقود، موثّق في `QA_REPORT.md`).

## 6) انحراف التوثيق عن الواقع

هذه النقطة أخطر مما تبدو: **قرارات المشروع تُتخذ بناءً على هذه الملفات.** ثلاثة
تضاربات مؤكدة:

**أ) بصمة SHA-256 مُعلنة منجزة وهي غير موجودة.**
`docs/الخطة.md` يقول: «كل إصدار ينشر الآن بصمة SHA-256 تلقائياً ✅ *(منجز)*».
الواقع: `release.yml` لا يحوي أي خطوة checksum. ملف `docs/CODE_SIGNING.md` يعرض
الكود المطلوب كـ **اقتراح للإضافة** — أي أن أحدهم قرأ الاقتراح وسجّله كإنجاز.
النتيجة: مستخدم يُنصح بالتحقق من بصمة لا وجود لها.

**ب) ثلاثة ملفات تصف بنية مهدومة.**
`QA_REPORT.md` و`DEVELOPMENT_PLAN.md` و`PRODUCT_FOUNDATION_ROADMAP.md` تشير إلى
`renderer/app.js`. الملف **محذوف** منذ التقسيم إلى 14 وحدة.

**ج) تقييم خاطئ لخطر قائم.**
`DEVELOPMENT_PLAN.md` يصنّف «الاستقرار المعماري 🔴 خطر — `renderer/app.js` = 2329
سطر». هذا **أُنجز فعلاً**. في المقابل، لا يذكر أي ملف العيوب الثلاثة في القسم 2 —
فالخطة تحذّر من خطر زال، وتصمت عن أخطار قائمة.

## 8) الترتيب ولماذا

```
أ ──────→ ب ──────→ ج ──────→ د
دقة      نظافة     أمن      توثيق
الأرقام   الأساس    التوزيع   ووصول
```

**لماذا (أ) أولاً؟** لأن العيب ع-1 قد يُخسِر المستخدم حسابه الممول، والعيبان ع-2
وع-3 يجعلان صفحة التحليلات تعرض أرقاماً خاطئة تبدو صحيحة. رقم خاطئ يثق به المستخدم
أسوأ من غياب الرقم — وهذا مبدأ مكتوب أصلاً في `DEVELOPMENT_PLAN.md`:
> «الدقة قبل الجمال. رقم خاطئ في منتج جميل أسوأ من واجهة بسيطة صادقة.»

**لماذا (ج) ليست أولاً رغم خطورتها؟** لأن ترقية Electron **لا يمكن التحقق منها في
هذه البيئة** — تحتاج بناء ويندوز حقيقياً. الدفعة (أ) بالمقابل قابلة للإثبات كاملةً
هنا والآن باختبارات تفشل قبل الإصلاح وتنجح بعده.
